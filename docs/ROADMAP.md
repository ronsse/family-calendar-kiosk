## M0 — Unblock

Goal: clear the two things that gate everything else.

- [x] Pi on the network and SSH-reachable from the server — key-only, passwordless sudo. Re-probed
      2026-08-23: **`eth0` is DOWN**, so the ethernet ssh alias reaches nothing; the wlan0 alias is
      the working one
- [x] **The Pi resolves `homeserver`** — done 2026-08-23 via Tailscale MagicDNS, which took over
      `/etc/resolv.conf` (nameserver 100.100.100.100, search `example.ts.net`). The **bare**
      name resolves: `homeserver` -> 100.64.0.2, and `http://homeserver:8123/` returns 200 in 48ms
      from the Pi. `DASHBOARD_URL` needed **no change at all**, so no IP is pinned anywhere and
      the "never hardcode the server's address" rule survives intact
- [x] **Join the Pi to the tailnet** — done 2026-08-23 by the operator. `wall-pi` =
      100.64.0.3, resolving from the server by bare name and FQDN. This also permanently fixes the
      dead ethernet ssh alias: one name that works from the server *and* `desktop-pc` regardless of which
      interface is carrying
- [x] Disable Tailscale key expiry on the Pi node — done 2026-08-23 via the Tailscale API;
      verified `keyExpiryDisabled=True`. The 180-day default would have blanked the wall six
      months in. Matches the server and `desktop-pc`, which were already set this way
- [x] **Test WiFi failover** — done 2026-08-23. eth0 is down and `wlan0` alone carried SSH, a
      full `apt` install and the Chromium session; the Pi survived a reboot on wlan0 only. The
      predicted side effect is real and now the running state: the server's ethernet alias for the Pi is
      dead and the wlan0 alias is the one that works
- [ ] Measure WiFi at the **final mounted position**, not the bench — acceptance:
      `iw dev wlan0 link` reports signal ≥ -67 dBm on 5GHz; below that, escalate to a USB
      adapter with an external antenna rather than tuning in software. The bench 94/100 says
      nothing about an exterior wall behind a 10lb metal-and-glass panel.
      **2026-08-25, current position:** -43 dBm, quality 67/70, on 5765 MHz (5GHz), 433 Mbit/s
      both ways, on the household SSID. That is 24 dB of headroom over the bar — but it is still not the
      mounted position, so the item stays open. Re-run after mounting; a reading this strong
      means the margin is there to lose.
- [ ] **Clear the under-voltage flag** — `vcgencmd get_throttled` now reads `0x0` (was
      `0x50000`) after the supply swap, temp 48.8 °C. Acceptance still wants a clean read a
      full day in, and the counter was reset by a reboot on 2026-08-23 — re-check before
      wall-mounting. An always-on display on a marginal supply is a slow failure.
      **2026-08-25:** `0x0`, 46.1 °C, `EXT5V_V` 5.13 V under a live Chromium session. Still
      does not close it: the counter was reset again by the acceptance reboot at 22:22, so this
      is a two-hour read, not a day. Re-check without rebooting in between.
- [x] DHCP reservation for the server — **closed 2026-08-25 as RESOLVED BY TAILSCALE, not done.**
      The acceptance was written against the LAN-address drift in PRD §3, and the wall no longer
      depends on the server's LAN address at all: the Pi's `/etc/resolv.conf` is generated by
      Tailscale with MagicDNS as its only nameserver, `homeserver` resolves to the tailnet address
      `100.64.0.2`, and the connection is DIRECT rather than relayed (`curAddr`
      is the Pi's wlan0 LAN address) — LAN speed, tailnet naming. Node key expiry is disabled on both
      nodes, which also closes the 180-day risk in CLAUDE.md.
      **The residual, recorded deliberately:** the Pi has no fallback resolver, so if
      `tailscaled` stops it cannot find the server across two feet of subnet. A reservation would
      not fix that — the Pi's `/etc/hosts` is cloud-init-managed, so there is nowhere durable to
      pin a name. A second path means a LAN nameserver that serves `homeserver`, which is a bigger
      change than the risk justifies today.

### Build

- [x] **Contracts frozen** — 2026-08-24. `db/schema.sql`, `src/types.ts`,
      `src/calendar/CalendarSource.ts`, `docs/api.md`, `db/seed.dev.sql`, hardened by
      [H3](design-review/H3-premortem.md) → [H2](design-review/H2-tournament.md) →
      [H1](design-review/H1-contract-review.md). A change to any of them now halts the swarm
- [x] **Unit A — persistence** — done 2026-08-24. `openDatabase` sets and *asserts*
      `foreign_keys` per connection (without it every FK in the contract is decorative);
      `migrate` is idempotent so it can run on every boot; `resolveAsset` walks
      explicit → category → `_default` and cannot return an empty image;
      `listBalances` LEFT JOINs from `child` so day one is zeroes rather than missing rows;
      `materializeRoutineRun` is idempotent *and* self-repairing. Acceptance met:
      `node --experimental-strip-types --test test/unit-a.persistence.test.ts` → 10/10,
      `npx tsc --noEmit` clean, `python3 db/verify-schema.py` → 22/22
- [x] **Unit B — `CalendarSource` adapter + staging/promote** — done 2026-08-24.
      `HomeAssistantCalendar` behind the frozen interface; `sync.ts` stages a generation and
      promotes it in one IMMEDIATE transaction, so a failed fetch leaves the previous
      generation whole. All-day detection keys on the **raw wire string, never the instant** —
      `2026-02-09T17:00:00-07:00` *is* midnight UTC and runs exactly 24h, so instant-based
      detection would turn a real 5 PM pickup into an all-day event. Boundary verified: nothing
      outside `src/calendar/homeassistant/` imports it. Atomicity proven with two connections on
      a file-backed WAL db, not asserted. 37 tests
- [x] **Unit G — design system** — done 2026-08-24. Tokens graded against a **10% flare term**
      rather than WCAG's 5%, because 225 nits behind etched glass in daylight is worse than the
      WCAG reference. Identity accents separate in *lightness* (1.72 / 2.12 / 3.64 pairwise) so
      they survive greyscale; no green in identity, because green means done. Floors: 14px type,
      64px tap, 2px stroke. Picture-band text sizes are `null`, not `0`. 38 tests, mutation-
      tested to prove they are not vacuous
- [x] **Schedule the sync off the Fastify event loop** — done 2026-08-25. `startSyncScheduler`
      runs it in a real worker thread and REFUSES to start rather than silently no-op; with no
      adapter configured it logs that it declined, which is the honest presentation of "no
      calendar" rather than an empty week that looks like a quiet one. Verified in the deployed
      container's boot log
- [ ] **Admin flow mapping `listSources()` into `calendar_source` rows** — assigning
      `colour_token`, `child_id` and `included` is an adult decision. **Partly closed
      2026-08-25**: `provision.ts --calendars <file>` applies `db/calendars.sql` additively, so
      changing what renders no longer means editing the household file and erasing the ledger.
      What is still missing is DISCOVERY — `listSources()` is never called, so you write entity
      ids by hand from `curl /api/calendars`. Owner: Unit F
- [ ] **Per-event icons** — HA supplies no category, so every event resolves the `calendar`
      fallback. `FetchedEvent.category` is plumbed through and honoured if someone authors a
      mapping. **Confirmed against real data 2026-08-25**: all 48 synced events carry
      `ico-calendar`, so the icon column currently carries no information at all
- [x] **`HA_BASE_URL` / `HA_TOKEN` injected via `op run --env-file`** — done 2026-08-25. The
      token is a 10-year HA long-lived JWT in 1Password as an `op://<vault>/<item>/<field>` reference;
      `stacks/wall/op.env` holds the REFERENCE and is gitignored. Boot log: `calendar sync
      scheduled`, then `3 ok, 0 failed, 48 events`
- [x] **Unit C — chores** — done 2026-08-24. Four assignment models; rotation is a pure
      function of `(chore, local_date)` folded with the chore id, so refreshing cannot re-roll
      it and two rotations sharing a roster do not shadow each other. Unsupported rrules are
      *refused and reported*, never silently treated as daily. Every transition carries the
      ownership predicate, and the ledger credit is pinned to the `child_id` returned by the
      UPDATE — so a caller-supplied id can never redirect points. 38 tests, including an
      exhaustive walk of all 120 operation sequences to depth 4
- [x] **Unit D — ledger** — done 2026-08-24. Balance is `SUM(delta)` on read with no second
      copy; redemption re-checks the balance *inside* the approval transaction so concurrent
      approvals cannot overdraw; `adjust` is idempotent on a caller-supplied `requestId`. The
      seam asserts its own precondition — `creditChoreApproval` throws if not already in a
      transaction. 35 tests
- [x] **Unit E — routines** — done 2026-08-24. Composes Unit A's materialization rather than
      reimplementing it; the time box ships as data and a test asserts the view's key set so a
      future `locked` flag fails the suite instead of failing at 6:00 AM in March. Icons are
      re-resolved at read time, since the un-validate guard protects only fallback targets.
      26 tests, with real DST arithmetic on both 2026 transitions
- [x] **Points ledger** — done 2026-08-25, and verified against the DEPLOYED wall rather than a
      harness: approving a claimed chore returned `ledgerEntryId: 1` and moved the balance to 1
      point / 10¢; approving the same assignment again returned `ledgerEntryId: null` and wrote
      no second entry, so a double tap cannot double-pay; a wrong PIN is `401`. The per-child
      toggle is live — the youngest has `ledger_enabled = 0` and his `cashCents` is `null` while his
      chores still run the full state machine. **Redeem and manual adjustment verified too**,
      same session, same deployed wall: a manual adjust is idempotent on `requestId` (the same
      id returns the same entry, never a second); a request for more points than a child holds
      is `409 insufficient_points`; a second request while one is pending is `409
      pending_redemption_exists`; the pending request appears in `WallSnapshot.redemptions`;
      approving it wrote entry 2 and took the balance 25 → 15 points, $2.50 → $1.50. Every test
      row was then deleted
- [x] **Routine runner — the flagship, and the reason this is a build.** Built and driven with
      real input events on 2026-08-25: tapping a step records `completedAtUtc` server-side and
      tapping it again revokes it. Time-boxed, daily-resetting, picture-led. **The acceptance
      criterion is not met and cannot be met by me** — "the youngest advances a routine to completion
      unaided" needs the youngest. His view renders with no text anywhere, which is the precondition
- [x] **Three per-child renderings** — done. Verified 2026-08-25 on the deployed wall by
      selecting each child in turn and walking both sections: zero buttons off-screen in any of
      the six combinations, and the picture band renders no word anywhere — not in the header,
      not on the section switch, not on a chore card. Streaks are still `null`: `WallSnapshot`
      carries no history, and adding it is a contract change
- [x] **Unit F — http + SSE** — done 2026-08-25. `node:http` (Fastify never installed; the
      route surface is small). The client's `localDate` wins, but only within ±1 day — building
      a date *materializes* it, so a kiosk with a dead RTC asking for 2000-01-01 would write
      runs forever; beyond the window it is `409`. The health probe is sized by measurement:
      it allocates 4–5 pages where a morning's materialization takes 2, and the test asserts
      both halves of H1 lens 4 on a page-constrained db. Sync runs in a real worker thread and
      refuses to start rather than silently no-op. 53 tests
- [x] **Unit H — three renderers** — done 2026-08-25. The band branch happens exactly once, at
      a keyed registry, so a source scan finds *zero* band conditionals anywhere — including
      the one file H2 §Q3 would have allowed. The picture band contains no text field and no
      text *mechanism*; quantity is pips computed in the domain so the renderer never sees a
      numeral, and "when" is an analog clock face with no digits. Every source scanner has a
      synthetic positive control, because a scan that silently stopped matching would report
      green forever. 83 tests
- [x] **Auth** — done. The wall carries a device token in `kiosk.env`, handed to the bundle as
      a URL *fragment* so it never reaches an access log; admin routes need that token plus
      `X-Parent-Pin`, verified per request, never a session. Wrong PIN is `401` and confirmed
      against the deployed wall. **The profile-wipe half of the acceptance is still unrun** —
      it needs a hand at the panel
- [x] **Unit I — bundle, compose stack, kiosk repoint** — done 2026-08-25. Vite bundle +
      the data layer Unit H left unwired (SSE by hand over `fetch`, since `EventSource`
      cannot send `Authorization`). The device token is issued to the *Pi*, not served in the
      HTML — serving it would hand a wall credential to any LAN device that can `GET /`. It
      travels as a URL **fragment**, so it never reaches an access log. Caught a render loop

- [x] **Unit J — acceptance walk** — done 2026-08-25. 45 e2e tests over real HTTP against a

### Harvest before building (PRD §5, ADR-0004)

- [x] Read DinkyDash `templates/index.html` (284 lines, **MIT — liftable**) — done 2026-08-25.
      The countdown primitive was already taken ("122 sleeps · Fri, Dec 25"). Two further
      things worth having, one taken:
      **Taken — the countdown GRID.** `grid-template-columns` rather than a wrapping flex row.
      Our routine steps were a wrapping row with a `maxWidth` cap, which is content-dependent
      and had to be re-tuned twice in one evening; a grid is the same on every band and for any
      label. Now `repeat(auto-fit, minmax(stepTileMinPx, 1fr))` with a per-band minimum, since
      a fixed column count fitted the fluent reader and pushed two of the emergent reader's
      steps off the screen.
      **Not taken — `html { font-size: clamp(13px, 3.2vmin, 24px) }`.** DinkyDash scales its
      root font with the viewport so one layout serves a 480px Pi and a living-room TV. We have
      exactly one panel of known size, and our floors (64px tap, 14px type) are promises about
      PHYSICAL size at 225 nits behind etched glass — `vmin` scaling would make them variable.
      Fixed px against a known panel is the right call here and the divergence is deliberate.
      Also noted: DinkyDash already uses **Nunito**, which our token file independently picked.
      Its per-child chore pills carry identity in hue alone, which our contrast rules forbid —
      identity here separates in lightness so it survives greyscale.

## M2 — Make it good on the wall

Goal: it is correct in M1; here it becomes something a 3-year-old reaches for.

- **Routine step imagery** ([ADR-0002](decisions/0002-image-generation.md)) — build-time assets
  committed to the repo; the wall never calls an image API. Cloud first (~$1 for the set).
  Judge the generated set against plain MDI glyphs **on the mounted panel** before committing —
  225 nits behind anti-glare glass punishes fine detail
- **Countdowns and the delight layer** — "3 sleeps until Christmas", birthdays, streaks. The one
  idea worth taking from DinkyDash outright
- **Parental controls** — beyond the M1 PIN: what a child can see, edit, and never touch
- ~~**Screen power**~~ — **DONE 2026-10-11.** Dark 21:00–06:00 (`SCREEN_ON_AT` / `SCREEN_OFF_AT`
  in the Pi's `kiosk.env`). `screen-power.timer` is a once-a-minute RECONCILER, not two one-shots,
  which also closes the old gap: an output found `off` in the day window is turned back on within
  a minute, so `wlopm --on '*'` in autostart is no longer the only recovery path, and nothing in
  `kiosk-watchdog` had to change. A touch on the dark panel wakes it (swayidle `resume`) and it
  goes dark again after 5 idle minutes; the hold expires after 30 regardless. A malformed time
  fails ON. `pi/scripts/test-screen-power.sh`
- **Phone admin (after v0.1.0)** — the grown-up screens reachable from a paired phone: pairing by a 6-digit code shown on the wall, the paired phone has no PIN guardrails, served at /admin on the same port. Decided 2026-10; no code yet.

## Icebox

Cut from the plan by [ADR-0004](decisions/0004-build-the-app.md) on 2026-08-24 — none of it
serves the four jobs in PRD §1, and together it is what turned this into a smart-home project.
Listed, not deleted: each may be a good idea later, none is a good idea now.

- **Local assistant** (was M3) — natural-language household queries. Would need a pinned
  tool-calling model and `OLLAMA_MAX_LOADED_MODELS=2`; guardrails as an allowlist, never a prompt
- **mmWave presence** via ESPHome (was M2) — sensor never purchased. The one sanctioned
  exception to the Google Home boundary, if it ever returns
- **Mealie** meal planning; **WallPanel** photo screensaver (both were M1/M4)
- **Photo→event AI** — needs a VLM; the RTX 2080 is full with an 8B. Drop it, carve a documented
  exception to the no-cloud invariant, or host it on `desktop-pc` (~2 min wake is fine for an async
  import). Price `desktop-pc` first
- Voice front-end on the panel's dual 2W speakers (reserved, unwired)
- Re-evaluate Magic Frame once it is past v1.x with more than one maintainer (ADR-0001)
